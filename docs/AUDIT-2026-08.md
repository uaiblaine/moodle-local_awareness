### H1. mustache-continue-on-error disables the Mustache gate on all four CI legs for a failure that is a redundant attribute

**Onde:** `.github/workflows/ci.yml`:15 · *Templates / Bootstrap 4-5*

**Evidência**

```
ci-502:
    uses: moodle-an-hochschulen/moodle-workflows/.github/workflows/moodle-plugin-ci.yml@main
    with:
      moodle-core-branch: MOODLE_502_STABLE
      mustache-continue-on-error: true
(repeated at lines 23, 31, 39)

templates/editor/action_bar.mustache:39
            <button type="submit" form="{{actionbar.formid}}" class="la-btn la-btn--soft" data-action="save-draft" name="submitbutton" value="savedraft">
templates/editor/action_bar.mustache:44
            <button type="submit" form="{{actionbar.formid}}" class="la-btn la-btn--brand" data-action="publish" name="submitbutton" value="publish" {{#actionbar.disablepublish}}disabled{{/actionbar.disablepublish}}>
```

**Por quê:** I ran the gate locally on both ends of the supported range (`mdl ci moodle-local_awareness --only mustache` and `--branch MOODLE_405_STABLE --only mustache`). On both, exactly two blocking lines exist and they are both in action_bar.mustache: `WARNING: HTML Validation error, line 14/17: The "form" attribute must refer to a form element.` Every other template reports `OK: Mustache rendered html succesfully`. The CHANGELOG entry justifies the override as "the editor's intentional cross-form `form=` submit pattern", but there is no cross-form submit: templates/editor/shell.mustache opens `<form {{{form_attributes}}} class="la-shell">` at line 38, includes `{{> local_awareness/editor/action_bar }}` at line 87 and closes `</form>` at line 95, so at runtime the buttons are already descendants of that form. `form_attributes` and `actionbar.formid` are both derived from the same captured moodleform id in classes/output/editor_page.php (lines 80 and 150-156), so `form="mform1"` points at the enclosing form and is a no-op. The lint only fails because it renders the partial in isolation.

**Impacto:** The Mustache lint is switched off for all ten templates on 4.05, 5.00, 5.01 and 5.02. Any future template that fails to render, has a broken example context, produces invalid HTML, or trips the embedded ESLint pass will be merged with CI green — the gate reports the failure and the workflow ignores it. The stated justification does not hold, so the override is buying nothing that a two-attribute deletion would not.

**Correção:** Delete the `form="{{actionbar.formid}}"` attribute from both buttons in templates/editor/action_bar.mustache (lines 39 and 44) — they are inside the form already — and drop `actionbar.formid` from the docblock and example context. Then remove `mustache-continue-on-error: true` from all four jobs in .github/workflows/ci.yml and record the removal in CHANGELOG.md.

> **Verificador adversarial:** Confirmed as written, with one addition that strengthens the fix: `form=""` is not a harmless no-op if `form_attributes`/`formid` ever come back empty — per HTML a present `form` attribute that matches no element id gives the button a null form owner, so the submit silently stops working. Deleting the attribute makes the buttons rely on their ancestor form and removes that failure mode as well. Fix as proposed: drop `form="{{actionbar.formid}}"` from action_bar.mustache:39 and :44, drop `actionbar.formid` from the docblock (line 9) and the example context (line 18), remove `mustache-continue-on-error: true` from all four jobs in .github/workflows/ci.yml, and record it in CHANGELOG.md (the existing line 37 justification must go, not just the flag).

### H2. Manage-notices page dies with a fatal TypeError once a targeted cohort is deleted or is not visible to the current manager

**Onde:** `classes/helper.php`:701 · *Lógica de negócio*

**Evidência**

```
classes/helper.php:695-702
    public static function get_cohort_name(int $cohortid): string {
        if ($cohortid == 0) {
            return get_string('notice:cohort:all', 'local_awareness');
        }

        $cohorts = self::built_cohorts_options();
        return $cohorts[$cohortid];
    }

classes/table/all_notices.php:237-240
            $cohorts = array_map(function ($cohortid) {
                return helper::get_cohort_name($cohortid);
            }, $awareness->get('cohorts'));
```

**Por quê:** The stored `cohorts` column keeps raw cohort ids forever; nothing removes an id when the cohort is deleted. `built_cohorts_options()` is built from `cohort_get_all_cohorts(0, 0)`, which also drops cohorts living in contexts the current user cannot view (moodle-405/cohort/lib.php:517-521 + `cohort_get_invisible_contexts()` at :615-635). When the key is absent, `$cohorts[$cohortid]` evaluates to null and returning null from a `: string` function throws in PHP 8's coercive mode — verified on the m405 container (PHP 8.3): `Warning: Undefined array key 9` followed by `TypeError: gcn(): Return value must be of type string, null returned`.

**Impacto:** Delete a cohort that any existing notice targets and /local/awareness/managenotice.php stops rendering — the admin gets a PHP fatal (TypeError) instead of the notice list, so notices can no longer be listed, reset, disabled or deleted from the UI. The same fatal hits any non-siteadmin holder of local/awareness:manage who lacks moodle/cohort:view on the category holding the cohort.

**Correção:** Guard the lookup: `return $cohorts[$cohortid] ?? get_string('notice:cohort:missing', 'local_awareness');` (or `'-'`, matching `get_course_name()`'s treatment of a missing course at classes/helper.php:717-722).

> **Verificador adversarial:** Accurate. Worth adding that the admin can still reach editnotice.php?noticeid=X&action=edit directly, so the site is recoverable without DB surgery — but the listing page itself stays fatal until the notice is fixed.

**Por quê:** `cohorts` is a multi-select autocomplete (classes/form/notice_form.php:140-146) but is absent from the marker-stripping list, unlike every other multi-select. Core only strips the forced-submission marker for `ajax`/`tags` autocompletes (moodle-405/lib/form/autocomplete.php:203-208); otherwise it falls through to `HTML_QuickForm_select::exportValue()`, which filters submitted values against the option list **only when the list is non-empty** (moodle-405/lib/pear/HTML/QuickForm/select.php:567: `if (is_array($value) && !empty($this->_options))`). > **Verificador adversarial:** Confirmed as written. Note the trigger is strictly 'zero cohorts visible to the saving user' — as soon as one selectable cohort exists, the option list is non-empty and core filters the marker out.

### H4. Unaliased COUNT() aggregate is read as ->count — the link-click report is blank on MariaDB

**Onde:** `classes/persistent/linkhistory.php`:83 · *SQL / portabilidade*

**Evidência**

```
83        $sql = "SELECT h.hlinkid, l.text, l.link, COUNT(h.hlinkid)
84                  FROM {local_awareness_hlinks_his} h
85                  JOIN {local_awareness_hlinks} l on h.hlinkid = l.id
86                  $wheresql
87              GROUP BY h.hlinkid, l.text, l.link";

277            $hlinkcount .= "<a href=\"{$count->link}\">{$count->text}</a>: " . $count->count . " <br/>";
299                return $linkcounts[$column]->count;
```

**Por quê:** The aggregate has no AS alias, so the returned column name is whatever the driver chooses. Verified live on both engines: PostgreSQL 17 names it `count` (`SELECT COUNT(1) FROM pg_class` -> header `count`), while MariaDB 10.11 names it after the literal expression text (`SELECT 1 AS hlinkid, COUNT(h.hlinkid) FROM (SELECT 1 AS hlinkid) h GROUP BY h.hlinkid` -> header `COUNT(h.hlinkid)`). Moodle's mysqli driver only lowercases keys (`array_change_key_case($row, CASE_LOWER)` at mysqli_native_moodle_database.php:1369), so the property is `count(h.hlinkid)`, never `count`. `$record->count` therefore resolves on PostgreSQL only.

**Impacto:** On MariaDB — half the CI matrix and a fully supported production DB — the "Links clicked" column of the acknowledged-notice report renders `<a href=...>text</a>: ` with the number missing, and every per-link column of the CSV/Excel download comes out empty instead of a click count. Each row also emits a PHP 8 `Undefined property: stdClass::$count` warning, which surfaces as debug output on a DEVELOPER-level site. The existing test (tests/awareness_test.php:269) only asserts `count($userlinks)` and never reads `->count`, so CI is green on both engines.

**Correção:** Alias the aggregate in classes/persistent/linkhistory.php:83 — `SELECT h.hlinkid, l.text, l.link, COUNT(h.hlinkid) AS clickcount` — and read `$count->clickcount` at classes/table/acknowledged_notice.php:277 and `$linkcounts[$column]->clickcount` at :299. Add an assertion on the returned count value to tests/awareness_test.php::test_user_hlink_interact so the alias is covered.

> **Verificador adversarial:** Finding stands as written. One refinement to the impact: `other_cols()` at :299 is only reached for the numeric per-link columns, which are defined only in the download branch of define_table_columns() (acknowledged_notice.php:122-124), so on MariaDB the on-screen 'Links clicked' column shows the anchor with a missing number while the CSV/Excel per-link columns are empty. The proposed fix is correct and complete; also note the same alias should be added before any new consumer is written, since the property name is the only thing tying the two files together.

### H6. get_contexts_for_userid only looks at local_awareness_lastview, so users with only link-click or acknowledgement rows are invisible to export and erasure

**Onde:** `classes/privacy/provider.php`:48 · *Privacidade / LGPD-GDPR*

**Evidência**


**Por quê:** A link click writes local_awareness_hlinks_his independently of any view record: amd/src/notice.js:71-74 binds click on every 'a' in the modal and calls trackLink() immediately, classes/helper.php:647-654 (track_link) inserts the linkhistory row, and classes/helper.php:244-245 sets target="_blank" on those anchors so the modal stays open. ### H7. Report Builder text columns emit raw database values — core's user entity escapes every one of them with s()

**Correção:** Add an escaping callback to every TYPE_TEXT/TYPE_LONGTEXT column in classes/reportbuilder/local/entities/{acknowledgement,notice,linkhistory}.php, mirroring core: `->add_callback(static fn(?string $value): string => s($value ?? None is covered by the five regexes. The narrower misses matter too: `fw-(bold|semibold)` misses fw-medium/normal/light/bolder, `lh-1` misses lh-sm/base/lg, `form-select(-sm)?` misses form-select-lg. (font-monospace, form-switch, gap-3, fw-medium and visually-hidden do appear in the 4.5 sheet, but only because sibling plugins polyfill them — e.g. `body.local-dimensions-bs4 .visually-hidden{` — so they are core-absent as well.)

**Impacto:** This test is the only observer in the whole pipeline for a defect class the house standard records as having shipped three times and been found on 90 sites. Today it passes 6/6 (verified: `mdl phpunit m501 local/awareness/tests/local/bootstrap_compat_test.php` → OK). The moment anyone writes `class="d-grid"`, `class="visually-hidden"`, `class="fs-5"` or `class="text-bg-primary"` in a template, the class resolves to nothing on Moodle 4.5, the layout silently breaks for every 4.5 site, and phpcs, the Mustache lint, stylelint and this test all stay green.

**Correção:** Replace the hand-written map in `bs5_only_utilities()` with the measured family list and make the patterns family-wide rather than value-specific: `/\bd-grid\b/`, `/\bvisually-hidden(-focusable)?\b/`, `/\bfs-[1-6]\b/`, `/\bfst-(italic|normal)\b/`, `/\btext-bg-[a-z]+\b/`, `/\bborder-[1-5]\b/`, `/\bratio\b/`, `/\btranslate-middle(-[xy])?\b/`, `/\bbg-body\b/`, `/\bvr\b/`, `/\bfont-monospace\b/`, `/\bform-switch\b/`, `/\bg-[0-5]\b/`, `/\b(top|start|bottom|end)-(0|50|100)\b/`, plus widened `fw-(light|lighter|normal|medium|semibold|bold|bolder)`, `lh-(1|sm|base|lg)`, `gap-(x-|y-)?[0-5]`, `form-select(-sm|-lg)?`. Add a comment recording the re-derivation command so the list is refreshed rather than trusted.

> **Verificador adversarial:** Downgraded from high to medium: the gap is entirely latent. I grepped templates/, amd/src/, classes/, report/, renderer.php and lib.php for the whole house list of BS5-only families and the only live hits are form-label and fw-bold (competency_picker_body.mustache:22), form-select (:25), fw-semibold (competency_picker_items.mustache:26), gap-2 (competency_rules.mustache:33 and :38), form-select (:44) and lh-1 (:54) — all five covered families, all polyfilled at the tail of styles.css. ### Web service local_awareness_search_roles has no capability check — any authenticated user can enumerate every role on the site

**Onde:** `classes/external.php`:265 · severidade Médio

**Impacto:** Any authenticated user (including a student, and including the guest account when guest access is on) can POST to /lib/ajax/service.php with methodname local_awareness_search_roles and receive the id, shortname and localised name of every role defined on the site, optionally filtered by context level via {role_context_levels}. That is the site's whole role taxonomy — including custom roles whose names disclose internal structure (e.g. "HR Auditor", "Board Observer") — handed to users who have no administrative capability at all. It is also an unauthenticated-by-capability query surface for scripted enumeration.

**Correção:** In classes/external.php::search_roles(), insert `require_capability('local/awareness:manage', $syscontext);` immediately after validate_context, using the same pattern already present in search_courses at lines 344-346: assign `$syscontext = \context_system::instance();`, pass it to `self::validate_context($syscontext)`, then require the capability. Add a PHPUnit test that calls the function as a plain user through call_external_function() and asserts a required_capability_exception.

### Manage-notices page re-reads the entire cohort table once per cohort per row — an N+1 of full table scans

**Onde:** `classes/table/all_notices.php`:238 · severidade Médio

**Impacto:** On a site with 20 notices on screen, each targeting 3 cohorts, one render of Site administration > Awareness > Manage notice issues 60 full scans of the cohort table plus 60 COUNT queries plus 60 rounds of context preloading — 120+ queries and 60× the cohort table materialised in PHP memory. The same page additionally issues one `$DB->get_record('course', ...)` per row via col_reqcourse -> helper::get_course_name (helper.php:717).

### Guest users are never rejected: all guest sessions share one userid, so the first guest dismissal permanently hides the notice from every later guest

**Onde:** `lib.php`:36 · severidade Médio

**Impacto:** An admin publishes a site-wide notice on a guest-accessible site. The first anonymous visitor closes it; from that moment the notice is suppressed for every subsequent guest visitor in every session, because they all read the same lastview row — the audience that the estimator counted as zero silently consumes the notice for everyone else. If the notice has reqack, the acknowledgement report shows one meaningless row (username `guest`), and repeated guest acknowledgements accumulate under that identity, corrupting the compliance evidence the report exists to provide. Add a PHPUnit test that calls get_notices as `$this->setGuestUser()` and asserts an empty notice list.

### Notice content is filtered at save time, so multilang and every other text filter is frozen to the author's language for all users; titles are never filtered at all

**Onde:** `classes/helper.php`:223 · severidade Médio

**Impacto:** On a multi-language site with the multilang filter enabled, a notice authored as `{mlang en}...{mlang}{mlang pt_br}...{mlang}` is resolved once, into whichever language the manager had active when they pressed Save, and every user on the site then sees that one language regardless of their own — the notice cannot be localised at all. The same freezing applies to every other filter (glossary auto-linking, activity names, MathJax markup), so the stored content silently rots when the filtered targets change. Notice *titles* have the opposite failure: because they never reach a filter, multilang markup is displayed literally in the modal heading and in the manage table. Because the content is stored with `noclean => true` and is never re-formatted at output, `$CFG->forceclean` and any later tightening of the site's HTML cleaning never applies to it.

**Correção:** Stop filtering at save time: in classes/helper.php::update_hyperlinks() replace `format_text($content, FORMAT_HTML, ['noclean' => true])` with the raw content (the DOMDocument pass only needs well-formed HTML, which `file_rewrite_pluginfile_urls` output already is), so the database keeps the author's source markup. Then filter at output: in classes/external.php::get_notices() run the record's content through `format_text($record->content, $record->contentformat, ['context' => \context_system::instance()])` and the title through `format_string($record->title, true, ['context' => \context_system::instance()])` before json_encode. Do the same in all_notices::col_title() and in the report builder notice entity.

### The site-wide navigation callback catches Exception only, so any Error thrown while resolving notices produces a fatal on every page of the site
